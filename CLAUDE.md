# Working notes for Claude

Jackson often takes a few days to get to a PR review, so after opening a PR a check-in or two is plenty. Hourly re-checks over several days are not needed.

Comments and docs in the code describe what was built; they're good evidence of how it works and weaker evidence of what was intended. Most design choices are deliberate, but when something looks wrong from a user's point of view (an admin setting up a deployment, a member using a page), say so plainly and ask, rather than explaining it away.

`docs/` describes what is built. A design that is not built yet goes in a GitHub issue titled "Design: ...", not in a file under `docs/`: issues are where Jackson and others see and manage them. Write the doc when the thing is built, and close the issue with it.

MCP keeps parity with the REST API: every route an account can call is also an MCP tool unless there is a written reason it shouldn't be. When you add or rename a route, decide its MCP side in `src/mcp/route-tools.ts` (usually one line in `ROUTE_TOOLS`; an exclusion needs its reason). `tests/unit/mcp/parity.test.ts` fails until you do. See docs/mcp.md, "Parity with the REST API".

The Assistant (`/ask`, docs/accounts.md) uses the MCP tool list as its own. A new tool that is not a read must be classified in `src/llm/tools/assistant-tools.ts` as held for the user or as running without asking, with its reason; `tests/unit/llm/assistant-tools.test.ts` fails until it is. When you add, move or remove a page under `web/app`, update the table in `plugin/skills/using-minerval/SKILL.md` (`tests/unit/plugin/using-minerval.test.ts`).

The caller skills in `plugin/skills/` carry the graph's principles to outside agents and are served over MCP (#620). When you change the constitution, a skill in `skills/`, a role prompt, a tool's name, or how a tool or agent behaves, update them in the same change: run `npx tsx scripts/sync-frontend-content.ts` and read the skills that mention what you changed. See docs/mcp.md, "Keeping them current".

A request that writes works at one label, where a deployment holds material at more than one. When you add a route that is not a read, decide where its label comes from in `src/server/request-labels.ts`: the row the request is about, or the label the person names when it starts something new, never a default. `tests/unit/server/request-labels.test.ts` fails until you do, and `tests/db/request-labels.test.ts` wants a request for it against a private row. A new place that returns a source's stored text to a person holds the permission to open raw sources (`src/raw-sources.ts`, `tests/unit/db/raw-source-text.test.ts`).

Two open PRs that each add a migration take the same number, so the second to merge always conflicts in `src/db/migrations`. Do not resolve that by hand: merge `origin/main`, leave the conflicts in the migrations folder as they are, and run `npm run db:renumber`. It renumbers this branch's migrations after main's and rebuilds the journal and snapshots. The journal's timestamps matter more than they look: production skips, without an error, a migration whose `when` is earlier than one it has already run (`scripts/migrations-lib.ts`). `tests/unit/scripts/migrations.test.ts` fails on a folder that is out of order. `.github/workflows/renumber-migrations.yml` does this on its own, on every push to main, for an open PR whose only conflicts are in the migrations folder or `web/content` (docs/infrastructure.md, "Migration renumbering").

`web/content` is generated by `scripts/sync-frontend-content.ts`. A conflict there is resolved by taking either side and running the script again, never by hand, and the same workflow does that too. Nothing written there may hold a figure over the whole set (a hash over every prompt, a length that counts the constitution, the time or commit of the sync): one such line is rewritten by every PR that touches any prompt, so every open PR would conflict whenever another merged.

Every setting has a row in `src/settings-registry.ts` that says who may change it (the machine alone, or the administrators in the app too) and whether a change applies live or at a restart. When you add an environment variable to `src/config.ts`, give it its row; `tests/unit/settings-registry.test.ts` fails until you do. Mark it `live` only if every reader calls `loadConfig()` when it uses the value: a scheduler's interval or a plugin's options read once at start are `restart`. Then run `npx tsx scripts/settings-docs.ts`, which rewrites the table in docs/settings.md (`tests/unit/settings-docs.test.ts`). A setting that is a choice about how the deployment works is the administrators'; one stays on the machine only if it is needed before the database answers, is part of the trust root, or is a fact about the machine (docs/settings.md, "What stays on the machine").

A setting added, retired or given a new default needs its line in `releases/next.md`, under `settings.added`, `settings.retired` or `settings.defaults_changed`: it is what tells a deployment's operator what an upgrade asks of them. `tests/unit/release-notes.test.ts` fails until it is there (`npm run release:check` says the same). Write there too, in prose, anything else a person upgrading should know, and an `operator_steps` line for anything they must do on the machine beyond the upgrade's own commands. `releases/settings.json` is rewritten only when a release is cut (`npm run release:cut`), never by hand. The version is one number for every part, written by `npm run version:set`, never in one file alone (docs/releases.md).

Read a node's current judgment through the `*_in_force` views (`src/db/schema.ts`), not by filtering on `is_current` by hand: a file under `src` that mentions `is_current` must be listed with its reason in `tests/unit/db/judgment-in-force.test.ts`, which fails until it is.

Call a model only through `src/llm/client.ts`, from inside a run that `withAgent` opened: that is what puts the call on the run log. `tests/unit/llm/logged-runs.test.ts` fails on a file that calls the client without opening a run, reaches a provider around the client, or keeps work off the log with `untraced()`, until the file is listed there with its reason. Where the log is kept as a record (`RUN_LOG_MODE=record`) the provider seam refuses a call with no run open. See docs/run-log.md, "No model call outside a run".

A model named by family alone ("Opus", "Haiku", "Fable", ...) means the newest of that family: newer models are as a rule better and cheaper. Defaults and pins take the newest unless a written reason says otherwise; check the provider's live model list, not memory.

## Constraints on agents

Agents, like anyone, need to know their affordances and the constraints they work under.

- Every limit an agent works under is stated to it up front, with its running state as it goes (the way the turn counter and the spend line do), and with the reason for it. Never enforce a limit an agent has not been told.
- Prefer money to counts. Where a resource is metered, the run's budget bounds it (docs/allocation.md, "Agents work to a budget they can see"); do not add a per-run or per-day count on top.
- A new hard limit needs a reason money cannot serve (injected text near escrow, a loop that has stopped spending, a caller waiting on the result, human attention nothing prices), written in the comment beside it. Add one thoughtfully, not by reflex.
